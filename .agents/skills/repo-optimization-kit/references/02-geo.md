# 02 · GEO（Generative Engine Optimization）

> SEO 的目标是"排在第一页"；GEO 的目标是**被 AI 直接写进答案里**。
> 当用户问 ChatGPT「怎么验证 API 中转站是不是真货」时，你的仓库要么出现在它的答案里，要么不存在。

## 1. 先理解 AI 是怎么挑素材的

主流答案引擎（ChatGPT 搜索、Perplexity、Claude、Google AI Overviews、元宝/豆包）大致做四件事：

1. **检索**：从索引里取回 3–10 个候选页面（GitHub README 是很常见的候选）
2. **切块**：把页面切成 100–500 字的片段，按问题匹配
3. **抽取**：优先捞"定义句、数字、表格行、步骤列表"
4. **归因**：答案里给出链接，通常只给 1–3 个来源

由此得到三条硬规则：

- **每段第一句就是结论**（切块时首句权重最高）
- **数字必须带单位与条件**（"17 秒"比"很快"可引用）
- **结构比文采重要**（表格一行就是一个完整事实）

## 2. 仓库作为语料的六个改造点

### ① llms.txt（AI 爬虫的入口文件）

放在仓库根目录，`https://raw.githubusercontent.com/{o}/{r}/main/llms.txt` 可直读：

```markdown
# 项目名

> 一句话定义 + 最硬的差异化事实。

## 核心文档
- [快速开始](...#快速开始): 三步跑通
- [工作原理](...#工作原理): 流水线
## 数据
- [patterns.json](...raw.../data/patterns.json): 机器可读规则库
## 引用
- [论文](...): 标题与年份
```

结构要求：`# 一级标题` → `> 摘要段` → 至少 3 个链接分组。
这是**约定俗成而非强制标准**，但越来越多工具与 Agent 会主动找它。

### ② 定义句前置

README 的第一个非标题段落必须能回答：「这是什么？给谁用？产出什么？」

```
❌ 本项目致力于打造业界领先的一站式解决方案……
✅ 给它一个 URL 和 API Key，它输出一份 0–100 分的验真报告。
```

### ③ 问答式结构（最容易被整段引用）

把"它能回答 N 个问题"做成表格，问题用**用户真实会问的原句**：

| 用户会问 | 我们怎么回答 |
|---|---|
| 我买的 GPT 是不是真的？ | 身份测谎 + 厂商自认矩阵 |
| 为什么它回答得比官方便宜？ | 经济学不可行性测算 |

FAQ 用 `<details>` 折叠，每个 `<summary>` 就是一条 query。

### ④ 事实表与机读数据

- 规格、档位、参数、对比 → 一律表格化
- 规则库、特征库、基线 → 另存 `data/*.json`，README 里链过去
- **散文是给人读的，表格和数据是给机器抽的**；两者都要有

### ⑤ 对比章节

AI 回答"X 和 Y 有什么区别"时，会优先找有明确对比表的页面。
写 `## 对比同类项目`，列「它有的 / 它没有的」，并诚实写清自己缺什么。
**承认缺点反而提升可信度**，也避免被当成营销页过滤掉。

### ⑥ 实体一致性

同一个东西在全文用同一个名字。别名要显式声明：

> 芯火 XH（`xh-forensics`，命令 `xh`，旧名 `api-detective`）

否则 AI 会把它识别成三个不同实体，分别给低权重。

## 3. 分发（GEO 的外部权重）

内容改完只是"可被引用"，还要"被看见"：

| 渠道 | 做法 | 注意 |
|---|---|---|
| awesome-lists | 找 3–5 个相关 awesome 仓库提 PR | 必须符合对方收录标准，别硬塞 |
| Hacker News / Reddit | Show HN 帖：一句是什么 + 一个真实数字 + 仓库链接 | 标题不要形容词 |
| 掘金 / 知乎 / 公众号 | 把一次真实取证写成故事，文末链仓库 | 平台内链权重高 |
| 技术博客 | 一篇"我们如何验证…"的长文，链回 README | 博客域名比 GitHub 更易被索引 |
| Release | 每次发版写清"解决了什么"，Release 页也会被索引 | 语义化版本 + 标题带主题 |

## 4. 怎么量（不要凭感觉）

建一个 **20 条查询集**，每月在 3 个引擎上手动跑一次，记录"是否提到你 / 是否给链接"。

```markdown
| # | 查询 | ChatGPT | Perplexity | 元宝 | 提及 | 链接 |
|---|------|---------|------------|------|------|------|
| 1 | 怎么判断 API 中转站是不是真的 | ✅ | ✅ | ❌ | 2/3 | 1 |
| 2 | 有没有检测模型被换芯的工具 | ... |
```

只看两个指标：**提及率**（答案里出现你的名字）、**归因率**（给出你的链接）。
低于 30% → 回去改 llms.txt/定义句/对比表；高于 60% → 开始铺渠道。

## 5. 反模式（会直接被降权）

- 关键词堆砌（"最好的 AI API 验真工具、模型检测、中转站检测…"）
- 全篇形容词、没有一个可验证事实
- 图片里塞正文（AI 读不到图里的字）
- 只有中文/只有英文（丢掉一半语料）
- 内容与代码不一致（README 写了某个功能，代码里没有）——**这是最致命的**
- 用 `<details>` 藏关键信息的同时没在正文给摘要（切块时可能只取到外层）

## 6. 验收

- [ ] `llms.txt` 可 raw 直读，结构完整
- [ ] README 前 300 字包含完整定义句
- [ ] 至少 1 张问答表 + 1 张事实表 + 1 个对比章节
- [ ] 至少 2 个机读数据文件，README 有链接
- [ ] 全项目实体名一致，别名有显式声明
- [ ] 20 条查询集已建立，跑过一次基线
- [ ] `CITATION.cff` 存在（学术/报告场景的引用入口）
